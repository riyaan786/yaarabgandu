# YAARAB BATTERY AND TYRE WORKS — customer documentation site

A single-page website documenting one customer's personal experience at
**YAARAB BATTERY AND TYRE WORKS**, Fraser Town, Bangalore — plus a private admin
dashboard for uploading phone photographs, recording facts, and reading messages
sent through the corrections form.

## Pages

| Route | What it is |
| --- | --- |
| `/` | Permanently redirects to the canonical single-page site. |
| `/yaarab-battery-and-tyre-works-fraser-town-bangalore` | The whole public site: hero, customer service, language & behaviour, pricing, reviews, footpath & safety, photos & evidence, contact and the corrections form. Anchor navigation (`#pricing`, `#evidence`, …) keeps everything on one page. |
| `/admin` | Private dashboard (sign-in required). |
| `/robots.txt`, `/sitemap.xml` | Generated by `app/robots.ts` / `app/sitemap.ts`; `/admin` and `/api/` are disallowed for crawlers. |

## Admin dashboard

Tabs: **Photos & evidence**, **Visit records**, **Pricing**, **Authorities**,
**Review timeline**, **Corrections inbox**, **Security**.

- **Photos & evidence** — take a photo with the phone camera (`capture` input) or
  pick one from the gallery, add a caption, capture date, category and
  description, then upload. Each photo can be published, unpublished, edited or
  deleted. Drafts never appear on the public page.
- **Visit records** — the factual details shown in the two experience sections.
  Blank fields are omitted, and a section's facts stay hidden until filled in.
- **Pricing / Authorities / Review timeline** — add, edit and delete entries; the
  public tables and timeline only render when entries exist.
- **Corrections inbox** — messages from the public form, private by default, with
  status changes (pending → reviewed → responded) and a mailto reply link.
- **Security** — rotate the access code (this signs out every other session).


### Environment variables (`.env.local`)

| Variable | Purpose |
| --- | --- |
| `ADMIN_INITIAL_CODE` | Used once to seed the administrator access code, which is immediately scrypt-hashed into SQLite. Rotate it from the Security tab afterwards; this value is ignored from then on. |
| `NEXT_PUBLIC_SITE_URL` | Canonical origin used for metadata, canonical links, `robots.txt` and `sitemap.xml`. |

## How the security works

- The access code lives only in the server-side database as a scrypt hash;
  nothing is stored in the browser.
- Sessions are random tokens in an **HttpOnly**, SameSite cookie with a TTL.
  Sign-in attempts are rate-limited per IP and failures add a small delay.
- State-changing admin requests are checked for a same-origin `Origin`.
- Uploads are size-limited, restricted to JPG/PNG/WebP, and verified by magic
  bytes on the server before being written to `data/uploads/`.
- Evidence files are stored **outside** `public/`; bytes are streamed only through
  `/api/media/[id]`, and only for published photos.

## Google Search Console verification

The HTML-file method is set up. The file is
`public/googledc0c2b1b335e05db.html` and its **entire** content is exactly this
53-character line, with no trailing newline and no HTML wrapper:

```
google-site-verification: googledc0c2b1b335e05db.html
```

It is served at the site root, and also at any nested path (via an `afterFiles`
rewrite in `next.config.ts` plus `app/google-verification-file/route.ts`), so it
works whether the Search Console property is a *domain* property or a
*URL-prefix* property that includes the page path:

```
https://<your-domain>/googledc0c2b1b335e05db.html
https://<your-domain>/<any-prefix>/googledc0c2b1b335e05db.html
```

Do not rename, move or edit the file, and keep it in `public/` when deploying —
removing it un-verifies the property. After verifying, submit
`https://<your-domain>/sitemap.xml` under **Sitemaps**.

### "Wrong content" — checklist

Search Console reports *"Your verification file has the wrong content"* when the
bytes it fetches do not match. Check, on the **deployed** domain (not localhost),
that the URL returns the line above and nothing else:

```bash
curl -s https://<your-domain>/googledc0c2b1b335e05db.html
# must print exactly: google-site-verification: googledc0c2b1b335e05db.html
curl -s -o /dev/null -w '%{http_code}\n' https://<your-domain>/googledc0c2b1b335e05db.html
# must print 200
```

Common causes, in order of likelihood:

1. **The file has not been deployed yet** — it only exists on your machine, so
   the domain still returns whatever the old site (or a 200 "page not found")
   serves there. Deploy, then re-verify.
2. **The token belongs to a different property** — if you copied the file name
   from another site's Search Console entry, the content can never match. Open
   Search Console for *this* property, choose **HTML file**, and use the file it
   offers there.
3. **A host/CDN is serving its own page at that path** (soft 404) or adding a
   wrapper. The `curl` above exposes this immediately.
4. **Whitespace/BOM in the file** — already avoided here: 53 bytes, no newline.
5. **URL-prefix mismatch** — covered by the nested-path rewrite, but only once
   the current build is deployed.

### Alternative: HTML tag method

If you would rather not depend on the file, paste the `content=` token that
Search Console shows for the HTML tag into `.env.local`:

```
GOOGLE_SITE_VERIFICATION=<token from Search Console>
```

then rebuild/restart. The token is rendered as
`<meta name="google-site-verification" content="…">` on every page. Leave it
blank and no tag is emitted (verified both ways).

## Data


## Legal tone

Copy is written in the first person and hedged (“I was charged…”, “in my
experience…”). Factual claims are paired with supporting evidence, and the
footer notice is retained verbatim:

> This website documents a customer's personal experience and observations.
> Information presented as personal experience represents the author's account.
> Readers should review supporting documentation and make their own assessment.

The business name is always spelled **TYRE**, never “Tire”.
